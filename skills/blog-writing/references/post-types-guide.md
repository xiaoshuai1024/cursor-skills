# 博客文章类型写作指南 v2

> 本文件是博客「1024 工程笔记」的**分类型写作规范**,与 `style-guide.md`(通用风格)配套使用。
> `style-guide.md` 管「怎么写」(语气 / 段落 / 排版),本文件管「写什么样」(每种文章的结构 / 篇幅 / 配图)。
> **所有新写 / 修订文章,先确定类型,再按对应章节执行**。
> 本文件是 `blog-writing` skill 的 reference,由 SKILL.md 在「定类型」步骤按需加载。

---

## 〇、总则(所有类型都适用)

### 最短篇幅:5000 字(除日常随笔外)

> 这是硬性规则。除「日常随笔 / Opinion」类短文外,**教程型 / 深度型 / 踩坑型 / 最佳实践型**四类,单篇**正文不少于 5000 字**。
>
> - 不够 5000 字,说明选题太薄,**拆成系列或合并主题**,不要硬凑。
> - 5000 字是**下限不是上限**:深度型常需 6000–10000 字,踩坑型常需 5000–8000 字,以讲透为准。
> - 「字数」指**正文中文字符数**,不含 front matter、代码块、图注、引用注释。

### 六类文章一览

| 类型 | 一句话定位 | 最短篇幅 | 命根子 |
|------|-----------|---------|--------|
| **教程型** Tutorial | 跟我做,你也能跑起来 | 5000 字 | 可复现性 |
| **深度型** Deep Dive | 讲透为什么 | 5000 字 | 逻辑严密 |
| **踩坑型** Postmortem | 我踩过的坑你别再踩 | 5000 字 | 真实思考 |
| **最佳实践型** Best Practices | 这么干最对 | 5000 字 | 可操作性 |
| **观点型** Opinion | 我怎么看 | 不设下限 | 论据强度 |
| **日常随笔** Essay | 我的日常 / 思绪 | 不设下限 | 真实感受 |

> 写之前先问自己:**这篇文章是哪一类?** 一篇文章只允许一种主导类型(可以借鉴其他类型手法,但骨架只能一个)。 hybrids 通常两头不讨好。

### 通用排版(沿用 `style-guide.md`,这里只强调与篇幅相关的)

- **段落 ≤ 4 行为佳,最多 7 行**(≤ 200 字)。
- **段间空一行**,杜绝文字墙。
- 标题只用 **一 / 二 / 三级**,不跳级。
- 代码块**精简**,只放关键几行,完整代码丢 GitHub / 附录。
- 5000 字以上的长文,**必须**用二 / 三级标题切分,每 800–1200 字一个二级标题。

## 一、教程型(Tutorial / How-to)

### 定位

手把手教读者完成一个**具体任务**。读者读完能照着复现,这是教程型存在的唯一理由。

**可复现性是命根子**:读者照着做跑不通,文章就是废的。

### 篇幅

- **5000 字起步,常 5000–8000 字**
- 不够 5000 字,通常意味着:步骤没讲透 / 前提没说清 / 报错没覆盖 / 选型理由缺失,补全这些自然就够
- 超过 10000 字,考虑拆成**系列**(Part 1 / Part 2)

### 内容构成(固定 7 段式)

1. **目标**(200–400 字):开篇一句话说"读完你能做出什么"。配一张**最终效果图 / 架构总览图**。
2. **适用人群与前提**(列表,300–500 字):
   - 读者应具备的前置知识
   - 环境、操作系统、运行时版本(**版本号必写死**)
   - 依赖项、账号、密钥准备
3. **整体思路**(400–600 字):先讲"我们要做什么、分几步、为什么这么分",配一张**全局流程图**。读者带着地图上路,才不会在步骤里迷路。
4. **步骤主体**(3000–5000 字,文章主体):
   - 每个步骤固定四件套:**做什么 → 为什么这么做 → 代码 / 命令 → 预期输出**
   - 每个步骤结尾配**运行结果截图**或**终端输出**,证明"我跑过"
   - 步骤之间用三级标题(`### 步骤 N:xxx`)分隔
5. **常见报错与排查**(500–1000 字,加分项但必须有):
   - 列出读者最可能卡住的 3–5 个坑
   - 每个坑:报错原文 → 原因 → 解决办法
6. **完整代码与产物**(200–400 字):
   - GitHub 仓库链接(指向具体 commit / tag,不要指向 main)
   - 关键文件完整清单
7. **下一步**(200–300 字):这篇文章之后的延伸方向、推荐阅读、relref 互链。

### 风格 / 语气

- **祈使句 + 第二人称**:"运行 `npm install`"、"你会在控制台看到..."。
- 不要写"我们接下来..."——读者是一个人,不是"我们"。
- **克制、确定**,不卖关子不抖机灵。
- 提到选型时直接给判断:"**用 Vite 不用 Webpack**,理由是...",不要"两者各有优劣"。

### 用词

- ✅ 推荐:"运行 / 创建 / 修改 / 检查 / 你会看到 / 预期输出"
- ❌ 避免:"我们可以尝试一下 / 让我们来探索一下 / 或许你可以 / 应该大概也许"

### 配图规范

- **每 2–3 个步骤配一张截图**(IDE / 浏览器 / 终端),证明可复现。
- 关键概念配 **draw.io 流程图 / 数据流图**(本仓库**禁止 mermaid**)。
- 截图要**圈出重点**(红框 / 箭头),不要全屏原图直接扔上来。
- 全局思路配**架构总览图**,放文章开头当"地图"。

### 写作前的强制检查清单

- [ ] 我自己**从零**照着这篇文章跑过一遍吗?(在干净环境里)
- [ ] 每个工具 / 库的**版本号**都写了吗?
- [ ] 每段代码都能**独立复制运行**吗?(不留隐含步骤)
- [ ] 报错截图配了**文字解释**吗?(光贴图不算)
- [ ] 步骤之间有**逻辑衔接**吗?(读者知道为什么下一步是这个吗)
- [ ] 字数 ≥ 5000?(不够就补「常见报错」「选型理由」「原理铺垫」)

## 二、深度型(Deep Dive / 原理剖析)

### 定位

讲清楚"**为什么会这样**"。读者已经会用了,想要底层理解。

**逻辑严密性是命根子**:任何一个推理跳跃,整篇文章的权威性就崩了。

### 篇幅

- **5000 字起步,常 6000–10000 字**,深度型本来就该长
- 但**长不等于啰嗦**——每一段都要推进论证,不能注水
- 超过 12000 字,考虑拆成**系列**(上 / 下篇)

### 内容构成(论证式结构)

1. **现象 / 问题钩子**(300–500 字):
   - 从一个**反直觉的现象**或**真实问题**切入
   - 例:"为什么 Vue 2 的响应式对 `arr[0] = x` 不生效?"
   - 这个钩子要贯穿全文,最后回扣
2. **直觉解释**(500–800 字):
   - 先用**大白话**讲一遍核心机制
   - **类比 / 隐喻**可以用,但必须准确(错误类比比不类比更糟)
   - 给读者一个"先记住这个"的简化模型
3. **逐层深入**(主体,3000–6000 字):
   - 从直觉 → 半精确 → 精确,**每层比上层更细**
   - 每深入一层,先说"上一层的解释在 X 处不严谨,真正发生的是..."
   - 配合**源码 / 数据 / 实验结果**佐证
4. **源码 / 实验佐证**(800–1500 字):
   - 贴**关键源码片段**(只贴关键几行,带行号 / 注释)
   - 或**自己设计的实验**(改一行代码看输出变化)
   - 严禁贴大段源码不解释
5. **边界与反例**(500–1000 字):
   - 这套机制**在什么情况下不成立**?
   - 有什么**已知坑** / 性能代价 / 历史包袱?
6. **心智模型总结**(300–500 字):
   - 给读者一个**能带走的思维框架**
   - "记住这三句话就够了:..."
7. **延伸阅读**(200 字):relref 互链 + 权威资料。

### 风格 / 语气

- **教师 / 解释者**口吻,自信但谦逊。
- 允许复杂,但**每一步都要让读者跟得上**——读者跟丢一次,后面就全废。
- 多用"为什么...因为..."、"关键在于..."、"本质上..."、"换句话说"。
- 不卖弄术语,**第一次出现的术语必须解释**。

### 用词

- ✅ 推荐:"本质上是 / 关键在于 / 这意味着 / 换句话说 / 严谨地说"
- ❌ 避免:"其实很简单 / 一看就懂 / 不言而喻 / 显然"(读者不懂才来看)

### 配图规范(最吃图的一类)

- **架构图 / 分层图 / 时序图**必备,一律用 **draw.io**。
- 复杂流程配**多张分解图**,而不是一张大杂烩(读者看不清就等于没画)。
- 源码解析配**高亮标注图**,关键行加注释箭头。
- **禁止用纯文字描述超过 3 层嵌套的逻辑**——必须画图。
- 心智模型部分配**Excalidraw 手绘风概念图**(对比 / 隐喻 / 心智模型用)。

### 写作前的强制检查清单

- [ ] 每个结论都有**源码 / 官方文档 / 实验**背书吗?
- [ ] 类比是否**准确**?(找个不懂的人验证)
- [ ] 读完读者能**向别人解释**这个机制吗?
- [ ] 每一层推理**没有跳跃**吗?(找Reviewer 专门盯推理链)
- [ ] 反例和边界讲清楚了吗?
- [ ] 字数 ≥ 5000?

## 三、踩坑型(Postmortem / 实战复盘)

### 定位

记录**真实场景里的一个问题**,从发现到解决的全过程。

**真实感和思考过程是命根子**:没有真实经历的"假踩坑"一眼就被看穿。读者要看的不是"答案",是"你怎么想到答案的"。

### 篇幅

- **5000 字起步,常 5000–8000 字**
- 重点不在解决方案有多炫,在**排查过程有多真、根因挖多深**
- 不足 5000 字,通常说明:**排查过程的弯路没写全 / 根因只停在表层 / 复盘太薄**

### 内容构成(6 段式,极重要)

1. **背景**(300–500 字):
   - 项目、技术栈、业务场景(2–3 句带过)
   - **不要写公司机密**,但要让读者有上下文
2. **问题现象**(400–800 字):
   - 具体表现 + **报错信息原文**(贴日志,不要转述)
   - 影响范围:线上 / 线下?数据损失?用户感知?
   - 当时**第一反应**是什么(为后面"弯路"埋伏笔)
3. **排查过程**(灵魂部分,2000–3500 字):
   - 按**时间线**记录思考:"第一反应是 X,试了发现 Y,于是怀疑 Z..."
   - **必须写出真实的弯路**:走过哪些死胡同、为什么后来放弃
   - 每个尝试配**当时的输出 / 日志 / 监控截图**
   - **不要事后诸葛亮**:不要把排查写成一帆风顺,那是假踩坑
4. **根因分析**(800–1500 字):
   - 深挖到本质,**问 5 个为什么**(Five Whys)
   - 不要停在"代码写错了",要挖到"为什么当时会这么写 / 流程哪里漏了"
   - 配**原理图 / 调用链时序图**,说明根因如何导致现象
5. **解决方案**(800–1500 字):
   - **方案对比**:列 2–3 个候选,说为什么选这个
   - 最终代码 / 配置(只贴关键几行)
   - **验证步骤**:怎么确认问题真的修好了
6. **复盘总结**(500–1000 字):
   - 沉淀成 **checklist / 规范**(让别人能直接用)
   - 个人 / 团队**学到什么**
   - 哪些**系统性改进**能避免这类问题(流程 / 工具 / 监控)

### 风格 / 语气

- **老兵讲故事**口吻,平实、不夸张。
- 允许自嘲("我第一反应是重启,没用")。
- **重点写"为什么"而非"是什么"**——单纯知识搬运没价值。
- 不抒情、不渲染("经过三天三夜的奋战"删掉)。

### 用词

- ✅ 推荐:"我当时的判断是 / 排查后发现 / 根因在于 / 教训是 / 如果重来我会"
- ❌ 避免:"经过不懈努力 / 皇天不负有心人 / 终于找到了 / 踩了不少坑才明白"

### 配图规范

- **日志截图 / 报错原文 / 监控图表**(真实性证据,不可省)。
- 复杂调用链配**时序图**(展示问题怎么一步步发生)。
- 解决方案配**前后对比图**(改前 vs 改后)。
- 根因分析配**draw.io 原理图**。
- 所有截图配**文字说明**,光贴图不算。

### 写作前的强制检查清单

- [ ] 排查过程有没有写出**真实的弯路**?(全是直线 = 假踩坑)
- [ ] 根因挖到**本质**了吗?还是停留在"代码错了"?
- [ ] 5 Whys 问到位了吗?
- [ ] 报错日志是**原文**吗?(不要转述)
- [ ] 复盘能被别人**直接复用**吗?(checklist / 规范)
- [ ] 字数 ≥ 5000?

## 四、最佳实践型(Best Practices / Guideline)

### 定位

把经验**提炼成可执行的规范**。读者要的是"我照着做就能做对"。

**可操作性和权威性是命根子**:模糊的"原则上要..."、"视情况而定"等于没写。

### 篇幅

- **5000 字起步,常 5000–8000 字**
- 偏**列表 / 表格 / checklist / 决策树**化,比叙述型更紧凑
- 不足 5000 字,通常说明:每条规范没给理由 / 没正反对比 / 没决策树

### 内容构成

1. **适用场景**(300–500 字):
   - 这套规范**适用于什么情况**?(团队 / 项目规模 / 技术栈)
   - **不适用**什么情况?(留边界,避免被无脑套用)
2. **核心原则**(500–800 字):
   - 先讲 **3–5 条**大原则(可记忆、可复述)
   - 每条原则一句话能说清
3. **具体规范**(主体,3000–5000 字):
   - 按主题分组(如「命名」「分层」「错误处理」「测试」)
   - **每条 = 做法 + 理由 + 反例**,固定三件套:
     - ✅ 推荐:`...` —— 理由:...
     - ❌ 避免:`...` —— 理由:...
   - 用**表格 / 列表**呈现,不要堆叙述
4. **决策树 / 流程图**(800–1500 字):
   - 遇到具体场景**怎么选**(用 draw.io 画决策树)
   - 例:"新增一个 API,该用 GET 还是 POST?看这张决策图"
5. **反模式集**(500–1000 字):
   - 列举**常见错误做法**,每条说明为什么错
   - 反模式比正模式更有教育意义
6. **可拷贝的检查清单**(300–500 字):
   - Markdown checklist 格式
   - 团队可直接用作 Code Review / 上线前自检

### 风格 / 语气

- **权威专家**口吻,直接给判断。
- **不留模糊空间**:"视情况而定"= 没用,要给"什么情况怎么办"的**决策表**。
- 多用祈使句和肯定句。
- 给理由时,理由是**专家判断**,不是"我觉得"。

### 用词

- ✅ 推荐:"应该 / 不要 / 必须 / 优先选择 / 禁止 / 例外情况是"
- ❌ 避免:"可以 / 也许 / 视情况 / 看需求 / 都行"(全是这种就是废话集锦)

### 配图规范

- **决策树 / 对比表 / 流程图**为主,一律 **draw.io**。
- 每条规范配**正反对比代码片段**(并列两栏)。
- 核心原则可配**Excalidraw 心智模型图**(帮助记忆)。
- 反模式配**图示**(错误结构示意图)。

### 写作前的强制检查清单

- [ ] 每条建议都给了**理由**吗?
- [ ] 有没有**正反对比**?
- [ ] 边界和适用场景讲清楚了吗?
- [ ] 读者能**直接拷贝**成团队规范吗?
- [ ] 决策树覆盖了主要分支吗?
- [ ] 字数 ≥ 5000?

## 五、观点型(Opinion / Essay)

### 定位

表达作者对某个**技术 / 趋势 / 做法**的判断。读者来看,是为了被说服或被挑战。

**论点和论据是命根子**:纯抒情或纯搬运没价值。

### 篇幅

- **不设下限**(短可几百字,长可 5000+),**不强制 5000 字**
- 够说清观点就行,不堆料——堆料反而稀释观点
- 但一旦展开论证,**至少 2000 字**才能立得住

### 内容构成

1. **核心观点**(开头直给,100–300 字):
   - 一句话说清你的判断
   - **不要藏着掖着**,读者没耐心猜
2. **为什么这么想**(主体,1000–3000 字):
   - 论据:**数据 / 案例 / 对比 / 亲身经历**
   - 多个论据**并列递进**,每个独立成段
   - 避免"我觉得",要"我的判断是基于..."
3. **反方观点**(500–1000 字,**关键,不可省**):
   - **主动陈述反对意见**,然后反驳
   - 不立靶子打,显得心虚
   - 承认反方有道理的部分,再说"但我仍然认为..."
4. **适用边界**(300–500 字):
   - 你的判断在**什么情况下成立**?
   - 留边界 = 留信任(不留边界 = 耍流氓)
5. **结论与行动建议**(200–400 字):
   - 重申观点 + 给读者**可执行的建议**

### 风格 / 语气

- **有态度的资深从业者**口吻,自信、不骑墙。
- 可以犀利,但要**对事不对人**。
- 留有分寸,承认不确定性("这个判断基于目前的实践,未来可能调整")。

### 用词

- ✅ 推荐:"我的判断是 / 关键在于 / 我认为 / 本质问题是 / 我承认... 但我仍然"
- ❌ 避免:"我觉得 / 也许 / 可能是对的 / 个人浅见 / 不喜勿喷"

### 配图规范

- **概念图 / 对比图 / 心智模型图**为主,用 **Excalidraw 手绘风**。
- 数据驱动的观点配**图表**(柱状 / 折线 / 散点)。
- 少用严谨架构图(这类文章不是讲架构)。

### 写作前的强制检查清单

- [ ] 观点**开头直给**了吗?(不要埋到第三段)
- [ ] 每个论据都**支撑观点**吗?(不支撑的删掉)
- [ ] 反方观点**主动陈述并反驳**了吗?
- [ ] 适用边界讲清楚了吗?
- [ ] 是**对事不对人**吗?

## 六、日常随笔(Essay / Daily)

### 定位

记录**个人日常、思绪、生活片段**,不强求技术深度。

**真实感受是命根子**:这一类**不受 5000 字约束**,长短自由,有感而发。

### 篇幅

- **不设下限,不设上限**
- 短可几百字(一条想法),长可数千字(一篇回忆)
- **不强求结构**,但**仍要分段**,不能文字墙

### 内容构成

- **自由**,可以是:
  - 一天的记录
  - 一段经历的回忆
  - 一个想法的展开
  - 对某事的吐槽 / 感慨
- 但仍建议:**开头有钩子,结尾有落点**,不要散漫到没形状

### 风格 / 语气

- **最自由的类型**,可以用第一人称、抒情、感叹
- 语气可以**口语化**,不像技术文章那么正式
- 但**仍然遵循** `style-guide.md` 的**段落规范**(≤ 7 行、段间空行)

### 配图

- **自由**:照片、截图、手绘、表情包都可以
- 不强制配图

### 检查清单

- [ ] 是**真实感受**吗?(不是为赋新词强说愁)
- [ ] 段落符合**通用排版规范**吗?(≤ 7 行、段间空行)
- [ ] 开头有钩子、结尾有落点吗?

## 七、类型识别:写之前先问的 5 个问题

不确定文章属于哪一类?按顺序问自己:

1. **读者读完要能做出什么东西吗?** → 能 → **教程型**
2. **核心是讲一个机制 / 原理 / 设计为什么这么设计吗?** → 是 → **深度型**
3. **核心是讲一个真实问题的排查过程吗?** → 是 → **踩坑型**
4. **核心是给一套规范 / 做法清单吗?** → 是 → **最佳实践型**
5. **核心是表达我对某事的判断吗?** → 是 → **观点型**
6. **以上都不是,只是日常思绪 / 记录?** → **日常随笔**

> 一篇文章只能有**一个主导类型**。可以借鉴其他类型的手法(如教程里穿插原理),但**骨架只能一个**,否则两头不讨好。

## 八、跨类型配图统一规范(本仓库强约束)

> 详见 `.agents/skills/drawio/SKILL.md`,这里只做摘要。**画图前必须先调用 drawio skill。**

### 工具选择

| 图的类型 | 工具 |
|---------|------|
| 架构图 / 部署图 / 数据流 / 分层架构 / 时序图 | **draw.io**(mxGraph XML) |
| 概念图 / 对比图 / 心智模型 / 流程梗图 | **Excalidraw**(手绘风) |
| ~~任何图~~ | ❌ **禁止 mermaid**(历史残留不算) |

### 配色规范(去 AI 味是核心)

- **白底为主**,最多 **1 个主色**(`#2563eb` 蓝 或 `#0f766e` 绿)+ 深灰文字 `#1e293b`
- **禁止**浅色填充(如 `fill:#e8f5e8`)、彩虹配色、渐变
- 字号 **14px / 12px** 两级(标题 / 正文)
- 箭头统一 `edgeStyle=orthogonalEdgeStyle`

### 标签规范

- **说人话**,不要对仗短语("输入层 → 处理层 → 输出层"✅,"承前启后 / 继往开来"❌)
- 坐标**手画**,不要等距对齐(避免 AI 味的机械感)

### 工作流

```
写源文件:static/diagrams-src/<slug>.drawio
    ↓ 导出(带 --embed-diagram)
静态文件:static/svg/<slug>.svg
    ↓ 文章引用
文章里:<img src="/svg/<slug>.svg" alt="...">
```

### 公众号同步:SVG 必须转 PNG

> 这是个踩过的坑:公众号对 SVG 支持极差,`<img>` 引用 SVG 在公众号编辑器里显示不出来,文章发上去一片空白。

**掘金/知乎**是 Web 平台,SVG 正常显示,博客站绝对 URL 或相对路径都行。

**公众号**必须用 PNG 位图。用 wechatsync 同步前:

```bash
# SVG 转 PNG(1600px 宽,公众号高清)
rsvg-convert -w 1600 static/svg/<slug>.svg -o /tmp/<slug>.png
```

然后生成公众号专用版文章:把 `<img src="https://站点/svg/<slug>.svg">` 换成 `<img src="/tmp/<slug>.png">`(本地路径)。wechatsync 会自动把本地 PNG 上传到公众号图床。

**多图时**:逐张转 PNG,文章里有几张图就转几张,全部换成本地路径再 sync。

### 配图密度(按篇幅硬性配额)

> 配图是去 AI 味、帮读者理解的核心手段,**宁可多不可少**。基准线:**5500 字配 3 张图,约 1 张 / 1800 字**。新文章按总篇幅(含代码)对照下表配图,**只能多不能少**:

| 文章篇幅(含代码) | 最少配图数 | 节奏说明 |
|------------------|-----------|---------|
| 5000–6500 字 | **3 张** | 开头总览 1 张 + 中段核心机制 1–2 张 |
| 6500–8500 字 | **4 张** | 总览 + 核心机制 + 对比 / 决策表 + 收尾心智模型 |
| 8500–12000 字 | **5–6 张** | 每个主要二级标题至少 1 张 |
| 12000 字以上 | **6 张起,无上限** | 每个二级标题都有图,深度型可达 1 张 / 1500 字 |

**配图分布原则**(不是堆在某一段):

- **开头**(前 800 字)必有 1 张总览图(架构图 / 流程图 / 模式对比),让读者建立全局心智模型。
- **中段**(文章主体)每个核心机制 / 关键决策都配 1 张图,不要连续 1500 字纯文字。
- **结尾**可配 1 张心智模型图或决策表,给读者带走的框架。

**配图类型选择**(每种类型各至少 1 张,不要全是同类):

- 架构图 / 分层图 / 数据流 / 部署拓扑 → 表达「**结构**」
- 时序图 / 流程图 → 表达「**过程**」
- 对比图 / 决策表 / 正反示例 → 表达「**判断**」
- 心智模型 / 概念图(Excalidraw 手绘风)→ 表达「**理解**」

**强制检查**:文章写完后,扫一遍全文,**任何连续 1500 字没有图**的段落,都要补一张图——这是硬性规则,不是建议。

## 九、通用「去废话词」清单(所有类型适用)

这些词一出现,文章质感就掉一档,**全部禁用**:

### 学习者口吻
- ❌ "今天来聊聊 / 跟大家一起学习 / 我们慢慢看"
- ❌ "我犹豫了很久 / 最早图省事 / 试了好几种"
- ❌ "踩了不少坑才明白 / 摸索了好久"

### 卖关子 / 感叹
- ❌ "结果呢? / 你猜怎么着? / 没错,就是它!"
- ❌ "经过不懈努力 / 皇天不负有心人 / 终于找到了"

### 万能废话
- ❌ "众所周知 / 毋庸置疑 / 不言而喻 / 显然"
- ❌ "其实很简单 / 一看就懂 / 不用多说"
- ❌ "视情况而定 / 看具体需求 / 各有优劣"(给判断!)

### 替换为
- ✅ "我的做法是 / 关键在于 / 本质上是 / 换句话说 / 我的判断是"

## 十、掘金爆款化经验(平台运营补充层)

> 本节是**平台运营经验**,不是写作基础规范。前面的章节一~九管「文章本身怎么写」,本节管「同一篇文章发到掘金怎么放大流量」。
> 与 `掘金爆款化改造SOP.md` 的分工:**SOP 文件管「旧稿怎么改造」(34 篇存量),本节管「新写文章怎么自带爆款基因」(增量)**。两者心法一致,场景不同。

### 1. 先理解掘金的流量分发逻辑

掘金不是「发了就有流量」,流量来自三层叠加:

| 层级 | 来源 | 关键杠杆 |
|------|------|---------|
| **L1 推荐池** | 算法按「点击率 + 完读率 + 互动率」分发 | **标题 + 封面 + 开头** 决定点击和完读 |
| **L2 等级加权** | 创作者等级(Lv1–Lv6),由掘力值决定 | **Lv5+ 文章自动推荐至首页**,这是质变门槛 |
| **L3 编辑手工推荐** | 官方编辑挑优质文上首页 / 入选「精选」 | 内容**干货密度 + 话题热度** |

**关键结论**:新号或低等级号,**标题和开头是命根子**(L1 决定生死);积累到 Lv5+ 后,等级红利开始复利(L2 放大流量)。所以**短期靠标题,长期靠持续产出冲等级**。

### 2. 标题公式(掘金标题≠公众号标题≠技术文档标题)

掘金读者刷信息流的速度极快,**3 秒决定点不点**。标题必须有钩子,四平八稳的标题没人点。

#### 高点击标题公式(挑一个,别混用)

| 公式 | 示例 | 适用类型 |
|------|------|---------|
| **数字 + 痛点** | 「百万行 Vue2→Vue3 升级:做一个敢跑在真项目的 codemod」 | 教程型 / 深度型 |
| **反差 / 反常识** | 「编译能过 ≠ 代码正确:一次『幽灵删除』事故复盘」 | 踩坑型 / 观点型 |
| **踩坑 / 事故** | 「多租户 SaaS 数据隔离:从一行漏掉的 tenant_id 说起」 | 踩坑型 |
| **从 X 到 Y** | 「从首屏 4 秒到 1 秒:我们怎么把 SSR 玩明白的」 | 教程型 / 最佳实践 |
| **疑问 / 挑战常识** | 「为什么我们团队禁用了 useEffect 的第二种写法」 | 观点型 / 最佳实践 |

#### 标题禁区(这些标题点击率极低)

- ❌ 「XX 架构设计与落地实践」(四平八稳,没钩子)
- ❌ 「XX 的应用与思考」(像论文,没人点)
- ❌ 「浅谈 XX」(浅谈 = 没干货的预判)
- ❌ 「XX 总结」(像周报,读者要的是干货不是总结)
- ❌ 纯英文标题(中文信息流里点击率砍半)
- ❌ 标题超过 30 字(信息流截断,看不到重点)

### 3. 开头 3 行决定完读率

掘金读者点进来后,**前 3 行决定他要不要往下滚**。开头必须有钩子,不能寒暄。

#### ✅ 推荐开头(钩子式)

- **痛点钩子**:「上周三凌晨,线上告警群炸了。一个本来只删一条数据的 SQL,把整张表干没了。」
- **反常识钩子**:「所有人都说 TypeScript 能减少 Bug,但我们的 Bug 数不降反升。问题出在 type 之外。」
- **数据钩子**:「首屏从 4 秒到 1 秒,没用 SSR,没用 CDN,只改了一个地方。」
- **TL;DR 钩子**(长文用):「这篇文章讲清一件事:为什么我们的多租户隔离最后选了行级 + Schema 混合方案。结论先放,过程慢慢说。」

#### ❌ 必删开头(背书式 / 寒暄式)

- ❌ 「我在 XX 领域做了十余年,主导过...」(背书,读者不在乎你是谁)
- ❌ 「随着 XX 技术的发展...」(套话,3 秒关页面)
- ❌ 「今天来聊聊...」(小白口吻,违反 `style-guide.md`)
- ❌ 「本文将介绍...」(像论文摘要,无趣)

### 4. 获得感密度(读者凭什么收藏 / 点赞)

掘金的互动数据(点赞、收藏、评论)直接决定 L1 推荐池的流量。读者点赞的唯一理由是「**这篇文章让我有获得感**」。

**每篇至少凑齐一个**(纯文字论述型文章最容易扑街):

| 获得感类型 | 形式 | 适用类型 |
|-----------|------|---------|
| **代码 / 配置** | 能直接抄走的片段 | 教程 / 最佳实践 |
| **对比表** | 优化前 vs 后、方案 A vs B | 踩坑 / 最佳实践 |
| **可复用清单** | checklist / 决策树 | 最佳实践 |
| **架构图** | draw.io 版,能存下来参考 | 深度 / 教程 |
| **数据 / 量化结果** | 真实量到的数,不是"提升很多" | 踩坑 / 最佳实践 |

> **铁律**:又长又水是掘金最忌讳的。5000 字以上的长文,如果干货密度撑不起来,**宁可拆成系列**,不要硬撑。

### 5. 排版细节(掘金读者特别敏感)

掘金读者对排版极其敏感,排版差的文章**技术内容再好也会被关掉**:

- **中英文之间加空格**:`使用 Vue 3 开发` ✅ / `使用Vue3开发` ❌
- **行高约字号的 1.5 倍**,段落之间**空一行**(沿用 `style-guide.md`)
- **代码块必带语言标识**:` ```js` 而不是裸 ` ``` `
- **专有名词大小写正确**:`GitHub` 不是 `github`,`iOS` 不是 `ios`
- **配图用 HTML img 控制宽度**:`<img src="..." style="width:100%;max-width:720px"/>`(markdown 的 `![]()` 在掘金会尺寸失控)
- **加粗克制**:每节加粗 ≤ 2 处,满屏加粗 = 没有重点

### 6. 互动引导(掘金专属,博客可不要)

掘金算法权重里,**评论数**是高质量信号。结尾留一句自然的互动引导:

- ✅ 「你遇到过类似的坑吗?评论区聊聊你的排查思路。」
- ✅ 「这套多租户方案你觉得哪里不成立?欢迎拍砖。」
- ❌ 「如果对你有帮助,麻烦点个赞👍」(生硬乞讨,反而掉价)

> ⚠️ **博客和掘金分开处理**:博客(`content/posts/`)里**不要带**互动引导(博客有 Giscus 评论系统),只有同步发到掘金时才加。

### 7. 标签与分类(影响 L1 推荐池的精准度)

掘金要求选 1–3 个标签,**标签越精准,推荐池越准,完读率越高**:

- 教程型:选**技术栈标签**(Vue / React / Node)+ 「前端」
- 踩坑型:选**问题域标签**(性能 / 内存泄漏 / 并发)+ 对应技术栈
- 深度型:选**主题标签**(架构 / 原理 / 源码)+ 技术栈
- 不要选「编程」「开发」这种**大词标签**(流量池太大,被淹没)

### 8. 发布时机(影响初始冷启动)

掘金的活跃高峰(国内开发者):

- **工作日**:早 9–10 点(上班摸鱼)、午 12–14 点(午休)、晚 20–22 点(下班后学习)
- **避免**:周末(流量腰斩)、节假日(基本没流量)
- **建议**:工作日**早 9 点前**或**午 12 点前**发布,赶第一波活跃峰

### 9. 掘金爆款检查清单(发布前对照)

在通用检查清单之外,发到掘金的文章**额外**过一遍:

- [ ] 标题有钩子(数字 / 反差 / 痛点 / 踩坑),不是四平八稳?
- [ ] 标题 ≤ 30 字,前 15 字能看懂?
- [ ] 开头 3 行是钩子,不是寒暄 / 背书?
- [ ] 中英文之间有空格?
- [ ] 代码块都带语言标识?
- [ ] 配图用 HTML img 控制宽度?
- [ ] 至少有 1 项「获得感」(代码 / 对比表 / 清单 / 架构图 / 数据)?
- [ ] 加粗 ≤ 每节 2 处?
- [ ] 标签选了精准的技术栈 / 问题域,不是大词?
- [ ] 结尾有自然的互动引导(仅掘金版,博客版去掉)?
- [ ] 发布时间赶工作日早 / 午活跃峰?

## 十一、与 `style-guide.md` 和 `掘金爆款化改造SOP.md` 的关系

| 文件 | 管什么 | 适用场景 |
|------|--------|---------|
| `style-guide.md` | **怎么写**:语气、段落、标题、代码、故事连贯 | 所有文章的通用底层风格 |
| `post-types-guide.md`(本文件) | **写什么样 + 平台分发**:每类文章结构 + 掘金爆款化 | 新写文章(增量) |
| `掘金爆款化改造SOP.md` | **旧稿怎么改造**:34 篇存量从 PPT 体改真人分享体 | 存量文章改稿 |

**三段优先级**:

1. 写新文章 → 先 `post-types-guide.md`(定类型 + 结构 + 篇幅),再 `style-guide.md`(落实语气和排版)
2. 改旧文章 → `掘金爆款化改造SOP.md`(语言去 AI 味 + 标题钩子化),配图部分两边规则一致
3. 同步发掘金 → 在博客版基础上,**加**本章第十节的爆款化处理(标题钩子、开头改写、互动引导、标签)

**冲突时**:博客以 `style-guide.md` + 本文件一~九为准;掘金版以本文件第十节为准(如博客不要互动引导,掘金版要)。

## 十三、AI 辅助写作的边界(新增)

> 本博客全程用 AI(Claude Code 为主)辅助写作,但**不是让 AI 代写**。AI 是工具,你是作者——观点、结构、事实判断必须由人掌控。下面是经过实战验证的边界。

### AI 适合做(交给它,人工抽检)

| 任务 | 说明 |
|------|------|
| **扩写初稿** | 给 AI 大纲和要点,让它把骨架填成段落初稿。效率最高的用法。 |
| **优化逻辑衔接** | 「这段和上段衔接生硬,帮我改顺」——AI 擅长润色过渡。 |
| **简化啰嗦句子** | 「这句话太长,拆成三个短句」——AI 拆长句比人快。 |
| **补例子 / 类比** | 「给这个概念补一个技术人秒懂的类比」——但要人工验证类比准确性。 |
| **查漏洞 / 反驳** | 「我这个论证有没有漏洞?扮演反对者挑刺」——AI 当 devil's advocate 很有用。 |
| **格式化 / 排版** | 列表化、加粗、表格转换、front matter 生成——纯机械活全交。 |
| **批量去 AI 味** | 见 SKILL.md「去 AI 味实战手册」的正则脚本。 |

### AI 不适合做(必须人工把关)

| 任务 | 为什么 | 人工怎么做 |
|------|--------|-----------|
| **定核心观点** | AI 没有立场,给的是「两边都对」的骑墙话,而观点型文章要的就是判断 | 你自己拍板,AI 只负责论证 |
| **定文章结构** | AI 倾向堆砌(把所有相关点都塞进去),不会做取舍 | 先用 `structure-toolkit.md` 的三步搭骨架法定结构,再让 AI 填充 |
| **事实核查** | AI 会编造 API 名、版本号、性能数据、引用来源,**且语气自信** | 所有 API / 版本 / 数据 / 引用,人工对照官方文档逐条核对 |
| **真实数据与经历** | AI 写不出你真实的踩坑过程,只会编「某次我遇到了...」 | 你的真实经历自己写,只让 AI 润色语言 |
| **标题最终拍板** | AI 标题偏四平八稳(「XX 的实践与思考」),缺钩子 | AI 生成 5 个候选,你按 `style-guide.md` 六模式重写 |
| **收尾结论** | AI 最爱用 checklist / 「希望对你有帮助」收尾,违反本博客硬规则 | 收尾必人工写,套用 `style-guide.md` 的结论式要求 |

### 确认流程(每篇发布前必走)

1. **初稿完成后**:通读全文,标记所有「AI 可能编造」的地方——API 名、版本号、数据、引用链接。
2. **事实核查**:逐一核对官方文档 / 自己的代码 / 监控截图,确认无误。
3. **观点审查**:问自己「这段话如果发到技术群,我会不会被反驳得哑口无言」——会的话说明论证不成立,补强或删掉。
4. **去 AI 味扫描**:跑 SKILL.md 的去 AI 味正则,清掉「回到本质」「我的判断是」等套话。
5. **防泄密**:确认没有公司内部代号、未公开项目名、真实客户数据、内部系统截图。`content/` 里的内容是公开的。
6. **人工终审**:你自己读一遍,觉得「这真的是我写的,是我真实想法」才发布。如果有任何一段让你犹豫「这是不是我说的」,重写那段。
