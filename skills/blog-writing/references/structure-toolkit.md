# 结构与骨架工具箱

> 本文件是 `blog-writing` skill 的 reference,在 SKILL.md「第 3 步 搭骨架」时按需加载。
> 解决的问题:`post-types-guide.md` 给了「六类文章写什么样」(模板),本文件给「为什么这么搭、怎么搭」(方法论)。
> 不照搬任何人的固定模板,而是把结构思维抽象成**通用工具**,套到六类文章里。

---

## 为什么需要这套工具

写文章最常见的失败,不是没内容,而是**内容堆砌、没有骨架**——读起来像把脑子里所有相关知识点倒出来,读者抓不住主线。

`post-types-guide.md` 的六类模板解决了「这一类文章该有哪些段」,但没解决:

- 这一篇的主张是什么?(全文的一句话总结)
- 段落之间是什么逻辑?(并列?递进?因果?对比?)
- 读者读完的「啊哈」点在哪?

**骨架工具回答这些问题**。下面四个工具,写任何类型文章都用得上。

---

## 工具一:金字塔原理(结论先行)

> 来源:芭芭拉·明托《金字塔原理》。一句话:**先把结论抛出来,再用支撑点撑住结论,自上而下展开**。

### 四条规则

1. **结论先行**:文章第一段(或第一节)就说清核心判断,不要把结论埋到最后。读者带着结论读细节,理解效率翻倍。
2. **以上统下**:每一层都是对上一层的支撑。二级标题支撑一级主张,三级内容支撑二级标题。不能出现「这节跟主题没关系」的段落。
3. **归类分组**:同层的支撑点要归类(不要把「性能」「部署」「测试」混在一节里)。
4. **逻辑递进**:同层之间有顺序——时间顺序、结构顺序、重要性顺序,不能随机排列。

### 反面 vs 正面(用「部署一个服务」举例)

❌ **流水账式(无金字塔)**:
> 先说安装,再说配置,再说启动,再说监控,最后说「这样部署比较好」。

读者读完不知道你想表达「这套方案好在哪」,只看到一堆步骤。

✅ **金字塔式**:
> 结论先行:「这套部署方案的取舍是——用单机换掉了 K8s,换来 10 倍的运维简化。」
> 三个支撑:
> - 为什么不需要 K8s(流量 / 团队规模)
> - 单机方案怎么保证可用性(夜间自愈 + 备份)
> - 换来了什么(运维成本对比数据)

读者一开始就知道你要论证什么,每个段落都在支撑这个论点。

### 在六类文章里怎么用

| 类型 | 金字塔顶端放什么 |
|------|----------------|
| 教程型 | 「读完你能做出 X」——目标和最终效果 |
| 深度型 | 「这个机制的本质是 Y」——核心论断 |
| 踩坑型 | 「根因是 Z」——开头就剧透根因,再讲排查过程 |
| 最佳实践型 | 「这套规范的核心原则是 W」——3-5 条原则先抛 |
| 观点型 | 「我的判断是 V」——结论直给(本来就该这样) |

**踩坑型特别注意**:金字塔原理和「按时间线讲排查过程」不冲突。可以这样组织:开头用一段话讲清根因(金字塔顶端),再用时间线讲你怎么排查到的(支撑过程)。读者既知道结论,又看到真实的推理。

## 工具二:MECE 法则(分得不重不漏)

> MECE = Mutually Exclusive, Collectively Exhaustive(相互独立,完全穷尽)。
> 一句话:**分类时分得不重叠、不遗漏**。

这是金字塔「归类分组」规则的具体落地。支撑一个主张时,你的子论点要是 MECE 的。

### 五种分类法

| 分类法 | 怎么分 | 技术场景例子 |
|--------|--------|-------------|
| **二分法** | A 和非 A | 同步 vs 异步;有状态 vs 无状态 |
| **过程法** | 按时间 / 流程阶段 | 请求进来 → 鉴权 → 路由 → 处理 → 响应 |
| **要素法** | 按整体与部分 | 前端 / 网关 / 服务层 / 数据层 |
| **公式法** | 按构成公式 | 性能 = 吞吐 / 延迟 / 资源占用;成本 = 人力 + 基建 + 维护 |
| **矩阵法** | 两个维度交叉 | 重要 × 紧急(四象限);复杂度 × 频率 |

### 怎么用(搭骨架时)

定完金字塔顶端的主张后,问自己:**支撑这个主张,可以分成哪几个维度?** 用上面五种之一。

例:主张是「E2E 测试要分级」。支撑维度怎么分?

- ❌ 随便分:「冒烟测试、关键路径测试、边界测试、回归测试...」——分着分着重叠了(关键路径和冒烟界限模糊)
- ✅ 用**矩阵法**:按「业务价值 × 执行成本」分成四级(P0 核心链路 / P1 高频功能 / P2 边界场景 / P3 回归兜底)——不重不漏,每级有明确标准

### MECE 不是绝对,是检查工具

实际写作中,完美的 MECE 很难做到(有些维度天然有重叠)。把 MECE 当**自检工具**用:写完子论点,问「这几个点有重叠吗?有遗漏吗?」——答「有」就调整,不必强求严丝合缝。

## 工具三:黄金圈法则(Why-How-What)

> 来源:西蒙·斯涅克《从为什么开始》。一句话:**先讲为什么,再讲怎么做,最后讲是什么**。

普通写作顺序是 What → How → Why(先讲做了什么),读者觉得「所以呢?」。黄金圈反过来:**Why → How → What**,先让读者认同动机,再讲方案。

### 适用场景

黄金圈**最适合**这两类文章:

- **「为什么选 X 方案」**(最佳实践 / 观点型):先讲为什么需要(痛点 / 目标),再讲怎么选,最后讲选的是什么。
- **「为什么这么做」**(踩坑型):先讲为什么这是个问题,再讲怎么排查解决,最后讲最终方案。

**不适合**:纯教程型(教程是 What → How 的,读者已经知道为什么要做)、纯深度型(深度型是讲原理,不是讲动机)。

### 结构对照

| 层 | 讲什么 | 占比 |
|----|--------|------|
| **Why** | 为什么要做这件事?什么问题 / 痛点驱动?不做会怎样? | 20-30% |
| **How** | 怎么解决?方案的核心思路 / 决策逻辑? | 40-50% |
| **What** | 最终做了什么?具体配置 / 代码 / 产物? | 20-30% |

**Why 是灵魂**:很多技术文章扑街,就是因为 Why 太薄(一句话带过)直接跳到 What(贴一大堆代码)。读者不懂为什么要做,代码再详细也没共鸣。

## 工具四:奥卡姆剃刀(能删则删)

> 奥卡姆剃刀:**如无必要,勿增实体**。放到写作上——**结构越简单越好**。

### 三条硬规则

1. **层级 ≤ 3**:一 / 二 / 三级标题够了,极少需要四级。如果发现要四级,要么内容该拆成新文章,要么该用列表代替。
2. **同层 ≤ 7 项**:一个二级标题下,并列的三级标题 / 列表项不超过 7 个(米勒数字,人脑短期记忆极限)。超过 7 个就分组,或合并。
3. **奇数优先**:讲「核心原则」「主要方案」时,3 个比 4 个好,5 个比 6 个好——奇数有「完整感」,偶数像没说完。

### 怎么用(写完后剪枝)

写完初稿,做一遍「剃刀扫描」:

- 这节删了,读者会少知道什么吗?——答不上来就删整节。
- 这三段讲的是不是同一件事?——是就合并成一段。
- 这个三级标题是不是可以并进上面那个?——能并就并。
- 这个列表有 9 项,能分组吗?——分 3 组各 3 项,比 9 项平铺好读。

**剃刀和篇幅的关系**:本博客篇幅由观点和内容决定,不设字数门槛(2026-08-26 取消各类文章字数限制)。剃刀是「**结构**上能删则删」——删掉冗余结构后若发现某观点没讲透,该补的是**信息密度**(加例子、加对比、加原理),不是把删掉的结构塞回来,更不是凑字。

## 三步搭骨架法(综合上面四个工具)

定完文章类型(`post-types-guide.md`)后,动笔前走这三步:

### 第 1 步:定主张(金字塔顶端)

用一句话写出「这篇文章的核心判断 / 结论 / 目标」。

- 教程型:「读完你能用 X 方案解决 Y 问题」
- 深度型:「Y 问题的本质是 Z」
- 踩坑型:「这次事故的根因是 W,复盘出的规范是 V」
- 观点型:「我的判断是 U,理由是 1/2/3」

**写不出这一句话?** 说明选题没想清楚,回去第 0 步(选题自检)。

### 第 2 步:MECE 拆分支

问:「支撑这个主张,分哪几个维度?」用 MECE 五种分类法之一拆出 3-5 个二级标题。

- 检查:这 3-5 个有重叠吗?有遗漏吗?(MECE 自检)
- 检查:每个二级标题都能独立支撑主张吗?(金字塔「以上统下」)

### 第 3 步:奥卡姆剪枝

扫一遍拆出来的结构:

- 层级超 3 层了吗?(剃到 3 层)
- 同层级超 7 项了吗?(分组或合并)
- 有没有「可有可无」的段?(删)

### 实例:搭一篇「为什么我们禁用了某测试实践」(观点型)

**第 1 步 定主张**:我们团队禁用了 X 写法,因为它制造了假安全感,真正的测试保障应该来自 Y。

**第 2 步 MECE 拆**(用二分法 + 要素法):
- 二级标题 1:为什么 X 制造假安全感(问题论证)
- 二级标题 2:为什么 Y 更可靠(替代方案论证)
- 二级标题 3:迁移路径(落地建议)
- 反方观点(承认 X 有用的场景)+ 适用边界

**第 3 步 剪枝**:反方观点和适用边界可以合并成「X 什么时候仍然有用」一节。迁移路径如果太长,拆成独立的最佳实践文章 relref 过来。最终结构 4 节,符合「同层 ≤ 7」。

## 骨架工具 vs 文章类型:不冲突,是叠加

| | 文章类型模板(`post-types-guide.md`) | 骨架工具(本文件) |
|--|--|--|
| **管什么** | 这一类的文章该有哪些段(固定结构) | 这一篇的主张怎么搭、段落怎么组织(通用思维) |
| **关系** | 骨架的「容器」 | 容器里每段的逻辑 |

例:踩坑型有固定 6 段(背景/现象/排查/根因/方案/复盘)。这 6 段是**容器**(类型模板定的)。但「排查」这一段内部,你可以用**时间线**(过程法)组织,「根因」这一段可以用**金字塔**(先说根因再展开)——这是**骨架工具**决定的。

**写文章的顺序**:先定类型 → 套类型模板的段落容器 → 再用骨架工具组织每段内部的逻辑。
