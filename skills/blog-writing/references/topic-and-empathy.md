# 选题方法论 与 读者同理心

> 本文件是 `blog-writing` skill 的 reference,在 SKILL.md「第 0 步 选题自检」时按需加载。
> 解决的问题:`post-types-guide.md` 假设「你已经知道写什么」,本文件补全「**写什么**怎么定」和「**写给谁**怎么想」。
> 选题决定文章成败的 60%,写作技巧只是剩下的 40%。一篇选错题的文章,写得再好也没人看。

---

## 第一部分:选题方法论

### 一、六类选题来源

写技术博客最大的障碍不是「写不出来」,是「不知道写什么」。下面六类来源覆盖了绝大多数能写的题材:

| 来源 | 说明 | 典型例子 |
|------|------|---------|
| **工作总结** | 把工作中解决的真实问题提炼成文章 | 一次线上事故的排查与复盘;某个性能优化的全过程 |
| **学习深挖** | 学一个技术时挖到的「为什么」,整理成深度文章 | Vue 响应式原理深挖;某框架的源码设计为什么这样 |
| **热点跟进** | 新版本 / 新工具发布,第一时间写实践 | React 19 新特性实测;某新 AI 编程工具上手 |
| **本质追问** | 对「大家习以为常的做法」问「为什么」,给出新视角 | 为什么我们不该写单用户 E2E;为什么覆盖率不是银弹 |
| **生活观察** | 把日常工作中的观察抽象成方法论 | 团队 Code Review 的常见反模式;技术选型的决策框架 |
| **巧用对比** | A 方案 vs B 方案,通过对比讲透 | SSR vs SSG;Vite vs Webpack;Claude Code vs Cursor |

**最稳的是前两类**(工作总结、学习深挖)——有真实经历撑底,不愁没内容。**最容易出圈的是后四类**(热点、追问、观察、对比)——但需要判断力和稀缺性。

### 二、选题三标准(缺一则弃)

定下一个选题后,用这三个标准过一遍:

#### 标准 1:分享欲——你有没有「想说」的冲动?

写之前问自己:**这篇我是不吐不快,还是「该更新了硬凑一篇」?**

- 分享欲强的选题,写起来流畅,读起来有热情。
- 没有分享欲的选题,硬写出来像完成任务,读者感觉得到。

**反面信号**:想到这个选题时的第一反应是「这个能凑 5000 字」而不是「这个我想讲清楚」——大概率缺乏分享欲,放弃。

#### 标准 2:稀缺性——网上已经有 100 篇一样的了吗?

搜一下你的选题关键词。如果前 10 条结果已经把你要讲的讲透了,你的文章必须有**稀缺角度**才能写:

- **新数据**:你跑过真实 benchmark,有别人没有的数据。
- **新场景**:同样的技术,放在别人没讲过的业务场景里(如「低代码里的多租户隔离」,而不是泛泛的「多租户」)。
- **新观点**:大家都在说 A 好,你基于实践说 A 在 X 场景反而有问题——反共识。
- **更深一层**:别人讲「怎么用」,你讲「为什么这么设计」。

**稀缺性不是「没人写过」**(那可能是没价值),而是「**别人没写到这个深度 / 这个角度**」。

#### 标准 3:对他人价值——读者读完能得到什么?

把选题翻译成「读者收益」:

- ❌ 「记录我今天学了 X」——这是日记,不是博客,读者收益为零。
- ✅ 「读完你能避开我踩的 3 个坑」——读者收益明确。
- ✅ 「读完你能理解 X 机制,面试 / 排查时用得上」——读者收益明确。

**判不准时**:假想你把标题发到技术群里,有人问「这文章讲了啥?」,你能不能一句话说清读者收益——说不清就是价值不明。

### 三、主题上升法(最重要的一招)

> 这是把「具体项目经历」变成「通用方法论」的核心技巧,来自腾讯 ruoyu 的方法论。

很多工作总结型选题,初看「太具体、太小众」,读者面窄。**主题上升法**把具体项目上升到通用方法论,读者面立刻扩大。

#### 三个层次

| 层次 | 选题 | 读者面 |
|------|------|--------|
| ❌ **就事论事(最窄)** | 「我们项目的微信境外定时器实现」 | 只有做境外支付的人关心 |
| ⚠️ **半上升(中等)** | 「微信境外支付里的定时器怎么设计」 | 做微信支付的人关心 |
| ✅ **上升到方法论(最广)** | 「如何实现一个分布式定时器:从需求到架构」 | 所有后端 / 做调度的开发者关心 |

**操作**:写之前问「**这个具体问题背后,是一个什么通用问题?**」

- 「我们的 CI 太慢」→「大型 Monorepo 的 CI 加速方法论」
- 「这个接口慢」→「高并发读接口的性能优化决策树」
- 「这次 AI 删了代码」→「AI 编程时代的代码完整性保障」

#### 反面:上升过度

主题上升要适度,不能硬拔:

- ❌ 「我们修了一个 typo」→「论代码质量的哲学」(上升过度,沦为空洞)
- ✅ 「我们修了一个 typo,但它导致了线上事故」→「从一行错误引发的链式故障:小改动的风险评估」

**判断标准**:上升后的主题,你的具体经历**仍然是核心论据**(✅);如果上升后具体经历变成了「举个例子」的点缀,就是上升过度(❌)。

### 四、「以正合,以奇胜」——选题的组合策略

> 借用孙子兵法:大部分文章靠扎实(正),出圈靠少数几篇(奇)。

- **「正」(80% 的篇数)**:工作总结、学习深挖型。不追求爆款,追求**扎实、可复现、长尾流量**。这些文章构成博客的基本盘,靠 SEO 和 relref 互链积累读者。
- **「奇」(20% 的篇数)**:热点跟进、反共识观点、对比横评。追求**短期爆发**。一篇「奇」文带来的流量,可能抵十篇「正」文。

**不要全是「正」**(博客会很稳但没人知道),**也不要全是「奇」**(流量不稳定,且「奇」文很累,难持续)。

**实操节奏**:每月 2-3 篇「正」,季度 1 篇「奇」。

### 五、选题自检清单(SKILL.md 第 0 步用)

- [ ] 我对这个选题有分享欲吗?(不吐不快 vs 硬凑)
- [ ] 网上同类文章多吗?我的角度稀缺在哪?(新数据/新场景/新观点/更深一层)
- [ ] 读者读完能得到什么,能用一句话说清吗?
- [ ] 这个选题能上升到通用方法论吗?(还是太具体小众)
- [ ] 5000 字撑得起来吗?(撑不起来是选题太薄,拆系列或换题)

## 第二部分:读者同理心

> 写作最大的敌人叫「**知识的诅咒**」(Curse of Knowledge):你知道的东西,你觉得理所当然;读者不知道,他读不懂你「跳过」的那一步。
> 专家口吻(`style-guide.md` 要求的)≠ 专家自嗨。专家是「**能用读者听得懂的方式讲清复杂事**」,不是「用术语把读者唬住」。

### 一、三类读者画像

动笔前先想:**这篇写给谁?** 不同读者,表述方式不同:

| 读者类型 | 特征 | 表述方式 |
|---------|------|---------|
| **同技术栈** | 和你用一样的技术,遇到一样的问题 | 可以用术语,直给方案,省略基础铺垫 |
| **跨技术栈** | 是开发者,但不熟你这个领域 | 术语第一次出现要解释,类比用他熟悉的领域 |
| **非技术 / 决策者** | 产品经理、技术管理者 | 讲业务影响和 ROI,少讲实现细节,多用图 |

**本博客的主要读者**:前端 / 全栈开发者,正往 AI 开发转型——和博主的成长线重合。所以默认按「**同技术栈 / 跨技术栈**」的混合体来写:可以用前端 / 全栈术语,但涉及 AI 的新概念要铺垫。

### 二、破除「知识的诅咒」——三个方法

#### 方法 1:找无背景的人读一遍

写完后,找一个**不懂这个主题的同事 / 朋友**读一遍,问他:

- 「哪一段你读着卡住了?」——卡住的地方,就是知识的诅咒。
- 「这个术语你懂吗?」——不懂的术语,第一次出现要加一句解释。
- 「读完你有什么疑问?」——读者的疑问 = 你该补的内容。

> 本博客用 AI 辅助写作时,可以让 AI 扮演「完全不懂这个技术的新手」,问它「这篇哪里你读不懂」——虽然不如真人准,但比没人验好。

#### 方法 2:自检模拟(没有真人验时)

通读自己的稿子,标记每一处:

- **用了术语但没解释的**——补一句通俗解释,或加 relref 到讲原理的文章。
- **跳了步骤的**(「显然,接下来就是...」)——补上中间那一步。
- **用了「我们都知道 / 不言而喻」的**——删掉这类词,真把那件事讲一遍。

#### 方法 3:用「教小白」的标准写初稿,再压缩

写初稿时,假设读者是小白,把每一步都讲透(甚至啰嗦)。改稿时,把**目标读者已经懂的部分**压缩掉——但保留那些「你以为读者懂、其实可能不懂」的部分。

这个顺序比「一上来按专家读者写」更安全:先写全 → 再删,比先省略 → 发现读者不懂再补,效率高。

### 三、写前 6 问(动笔前问自己)

定完类型和选题后,动笔前回答这 6 个问题(可以写在草稿顶部,写完删掉):

1. **写给谁?**(三类读者画像的哪一类)
2. **他已经知道什么?**(前置知识,不用铺垫的)
3. **他不知道什么?**(这篇文章要教的)
4. **他为什么关心这个?**(他的痛点 / 收益是什么)
5. **他会用什么顺序读?**(从头读 vs 跳读找答案——决定结构)
6. **他读完该做什么 / 带走什么?**(行动建议 / 核心认知)

第 5 个问题尤其重要:**技术博客读者大量是「跳读找答案」的**(从搜索引擎进来,只想看某一段)。所以:

- 标题 / 章节标题要**能让跳读者直接定位**(这呼应了 `style-guide.md` 的「关键技术词前置」和 SEO 长尾思维)。
- 每个二级标题下,**前两段就要给出该节的核心结论**——跳读者读这两段就够,想深入的再往下读。
- 不要「埋伏笔到最后揭晓」——跳读者根本看不到最后。

### 四、同理心 vs 专家口吻:不矛盾

`style-guide.md` 要求「权威自信、直接给判断」,本文件要求「站在读者角度、破除知识诅咒」。这两者不矛盾:

| | 专家口吻 | 读者同理心 |
|--|---------|-----------|
| 讲**判断**时 | 权威、直接、不骑墙 | — |
| 讲**过程**时 | — | 循序渐进、不跳步 |
| 讲**术语**时 | 自信使用 | 第一次出现解释清楚 |
| 讲**结论**时 | 不 hedge(别「也许/可能」) | 但要讲清适用边界 |

**一句话总结**:**判断要硬(专家),讲解要软(同理心)**。观点要自信,但要把读者「为什么该信你」讲清楚——这就是同理心。
