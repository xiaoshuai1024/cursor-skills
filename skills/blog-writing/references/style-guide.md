# 博客写作风格指南 v3

> 本文件是博客「你的博客」的统一写作与修订规范，基于个人技术博客排版范例研究 + 博主定位 + 行业方法论综述（掘金 / 知乎 / freeCodeCamp / 腾讯 ruoyu / Phodal）。
> **所有文章(新写 / 修订)都以本文件为准**。
> 本文件是 `blog-writing` skill 的 reference，由 SKILL.md 在「起标题 / 写正文 / 修订」步骤按需加载。

---

## 一、核心定位(最高准则,贯穿全站)

这个博客讲**一个完整的故事**:博主从**前端**出发,成长为**全栈架构师**,再转型为 **AI 开发**实践者。

每一篇文章都是这条成长线上的一个节点,要同时传递三样东西:

- **能力**:我具体能做什么、做到了什么程度(用真实的事和数据说话)。
- **成长**:这段经历让我在哪个维度变强了。
- **认知**:我对这件事的理解、判断、观点。

> 写每篇前先问:它在「前端 → 全栈 → AI 开发」这条线的哪个位置?展示的是哪项能力、哪次成长、哪个认知?开头要让读者感觉到这个位置。

## 二、语气:AI 使用专家,不是小白

博主现在的身份是 **AI 使用专家**。语气要**权威、自信、分享能力**,像领域专家在讲自己熟练掌握的东西。

### ✅ 要
- 直接给判断、方案、原则("我的做法是…""关键在于…")。
- 用陈述、肯定的语气。
- 提到 AI 工具,以 **Claude Code、Codex** 为主(主力 Claude Code),**不要再列 Cursor**。
- 可以讲"为什么这么做",但原因是专家判断,不是"我试过才发现"。

### ❌ 不要(从旧稿清掉)
- 小白/摸索视角:"我犹豫了很久""最早图省事""踩了不少坑才明白""试了好几种"。
- 提及原文/复述提示词:仿写或衍生文章里**不要**出现"看到一篇《xx》""原文说""那篇作者""原文提到"这类对原作的引用,更不要复述任务提示词的内容;文章必须独立成立。
- 学习者口吻:"今天就来聊聊""跟大家一起学习"。
- 卖关子/感叹:"结果呢?""你猜怎么着"。
- 踩坑可以提,但要讲成"这个问题的本质是…所以我定了…",而不是"我踩了个坑"。

## 三、排版规范(来自技术博客范例研究)

> 来源:中文技术文档写作风格指南、掘金 / 博客园排版规范、MDN 写作规范等(见文末)。

### 段落(旧稿的主要问题,最重点)
- **一段一个主题**。
- **每段 ≤ 4 行为佳,最多不超过 7 行**(约 ≤ 200 字,绝不超 250 字)。长段落必须拆。
- 段落之间**空一行**。
- 杜绝"一整块文字墙"。

### 时间格式(2026-08-14 定规)
- 文章里出现的时间一律用**完整年月日时分秒**格式:`2026-08-13 11:56:32`。
- **禁止**简写("8 月 13 日""13 号""昨天""中午")和模糊表述;UTC 时间必须带时区标注(如 `2026-08-13 11:56:32 UTC`),本地时间带 `+08:00`。
- 只涉及日期不涉及时刻时也要完整年月日:`2026-08-13`,不写"8 月 13 日"。

### 收尾(最反 AI 味的地方,硬规则)
- **禁止用「检查清单 / 落地清单 / Checklist」收尾**。这是最典型的 AI 味套路——一篇技术文章最后甩一张 `- [ ]` 复选框列表,读起来像 GPT 生成的总结模板。
- 收尾必须是一段**结论**:回到这篇文章的核心判断,用 1–3 段陈述句收住,讲清楚"我最终的观点是什么 / 这件事的本质是什么 / 读者该带走什么"。
- 结论可以是:对争议的明确站队、对本质的一句话定性、对前面所有论述的收敛。**不要复述要点**(那是 PPT 的活,不是文章的活)。
- 中间段落可以用列表(那是并列要点),但**全文最后一段不能是列表**,必须是连贯的文字结论。
- 同理禁止的其他 AI 味收尾:"以上就是…的全部内容""希望对你有帮助""以上就是 X 的 N 种方法,你学会了吗"。

### 标题(文章标题,写作第一步,最重要)

> 标题是文章的脸面——掘金官方的说法是「读者看文章的第一眼就是标题」。一个好的标题决定了一篇文章会不会被打开。下面这套规则综合了掘金 / 知乎 / 博客园的高赞实践和技术读者的阅读心理,新写文章 / 改写文章**必须对照执行**。

#### 硬规则(违反即返工)

- **先出 10 个分档位候选让用户选(默认流程)**:写正文前先生成 **10 个标题**,覆盖从朴素情绪向 → 口语判断 → 抓眼球/夸张的不同档位(每档 3-4 个),交给用户挑;选定后再写正文。不要只给一个、不要替用户定。
- **长度 15–30 字**。太短(<12 字)信息不足,太长(35 字+)信息过载。技术读者扫信息流只看标题前半段,核心信息要能在一屏内看完。
- **结构自由,拒绝模板化**。主副结构(冒号 `:` 分隔)是**可选的一种,不是默认**——多篇连用「主题:说明」是同质化的第一来源。主标题直接立钩子、一句陈述句、一个反问,都行。例:`DeepSeek 便宜到骨折还拿了世界第二,但我劝你先别切`——无冒号,直接立反差。
- **关键技术词前置**。读者关心的是「这篇跟我有没有关系」,技术栈名、问题领域要放在标题前半段,不要埋在副标题末尾。
- **一眼说清讲什么**。这是底线——读者点进去发现货不对板,比标题平淡更伤口碑。标题可以有张力,但**内容必须兑现标题的承诺**。
- **禁止纯博眼球的标题党**。「震惊!」「看完我沉默了」「XX 天速成」这类与内容无关的情绪词一律不用。标题党不是「有吸引力」,而是「题文不符」——夸张可以,前提是内容配得上。

#### 高赞标题的六种模式(套用即可)

技术文章标题不是玄学,有固定模式。写之前先定这篇文章属于哪种类型,套对应模式:

| 模式 | 适用文章类型 | 结构公式 | 例子 |
|------|------------|---------|------|
| **数字 + 痛点** | 教程 / 最佳实践 | `数字 + 痛点 : 具体方案` | `19 个 JavaScript 实用简写技巧` / `改一处配置五个 IDE 生效:跨工具配置同步方案` |
| **揭秘 / 你所不知道** | 深度型 | `你所不知道的 / 重新认识 + 主题` | `你所不知道的 CSS 阴影技巧` / `重新认识 Event Loop` |
| **踩坑 / 实战复盘** | 踩坑型 | `记一次 + 真实事故 + 排查` | `记一次线上 OOM 排查全过程` / `从一次删库事故说起:数据安全 SOP` |
| **决策 / 为什么** | 最佳实践 / 观点 | `为什么我 + 放弃/选择 + 方案` | `为什么我放弃了 Redux` / `为什么我不再写单用户 E2E` |
| **对比 / 选型** | 最佳实践 | `方案 A vs 方案 B + 结论` | `2024 年前端状态管理方案横评` / `Saga 还是 Redux:大型项目怎么选` |
| **成长 / 路径** | 观点 / 日常 | `如何在 + 时间 + 达成 + 目标` | `如何在三年内成长为技术专家` / `从 CRUD 到架构师的进阶路线` |

一篇好标题往往**组合多个模式**(比如「数字 + 痛点」叠加「决策」)。组合时主标题负责抓眼球,副标题负责说清楚。

#### 去同质化:掘金冲突感 + 抖音抓眼球(最重要的进化)

> 上面六种模式是「写出合格标题」的底线,但**多篇套同一套模式,就会长出一模一样的脸**——「XX:YY」结构连用、数字+痛点反复出现,读者一滑就知道是同一个博客,这就是最重的 AI 味。**标题的差距不在「合格」,在「让人想点」。**

**核心心法:前 5-8 字埋冲突点,每篇只打一个冲突。**

- **抖音法则**:标题前 5 字必须埋钩子——冲突 / 反常识 / 反差 / 悬念。读者视线扫过前 5 字就决定点不点。
- **掘金法则**:冲突感(为什么 / 永远不要 / 别)、数字具象化(三倍 / 2.3 / 骨折)、悬念提问(还在说…?)。

**五步写标题流程(替代「直接套模式」):**

1. **先写一句内容钩子**:这篇文章最反直觉的结论是什么?一句话说清楚。
2. **前 5-8 字埋冲突**:最锋利的词放最前面,不要用「介绍 / 聊聊 / 关于」开场。
3. **只打一个冲突点**:数字 / 反差 / 反常识 / 悬念,占一样就够;塞满反而每条都弱。
4. **口语化 + 情绪词**:翻车 / 白装 / 骨折 / 当场 / 甩开 / 一文不值 / 别切。像人话,不像官方公告。
5. **内容兜底**:夸张可以,但标题里每一句都要有正文论据——「便宜到骨折」背后要有价格对比数据。

**情绪档位(从克制到狠,停在档位 2):**

| 档位 | 特征 | 例子 | 判断 |
|------|------|------|------|
| 档位 1 | 冲突,偏理性 | `DeepSeek 编程冲上世界第二,我为什么劝你先别切` | 及格 |
| 档位 2 | 打脸感,情绪词加码 | `DeepSeek 便宜到骨折还拿了世界第二,但我劝你先别切` | **推荐,到此为止** |
| 档位 3 | 标题党 | `震惊!DeepSeek 杀疯了!` | 禁用——触发限流、透支信任 |

> **上限提示**:档位 2 是「狠但真实」的天花板。再往上就是「震惊 / 吓尿 / 吐血」级标题党,会触发平台限流、透支读者信任。拿不准时向档位 2 收敛。

#### 强调「SOP」主题时怎么写

当文章内容本身是一套标准操作流程(SOP)时,要在标题里体现,但**不要用文件编号式的硬贴标签**:

- ❌ `【SOP】数据零丢失的最后一道闸:...` —— `【SOP】` 前缀像内部文件编号,读者扫到会联想到「枯燥的操作手册」,降低点击欲
- ❌ `XXX 的标准做法` / `XXX 的标准 SOP` —— 过于平淡,像内部文档章节名,缺少「这跟我有什么关系」的钩子
- ✅ `备份 ≠ 能恢复:3-2-1 备份与每月强制演练的完整 SOP` —— SOP 放副标题末尾,不抢主标题位置,用 `≠` 制造反差吸引点击
- ✅ `改一处配置五个 IDE 全生效:我的跨工具配置同步 SOP` —— 主标题讲痛点和效果,副标题收尾点明 SOP 性质
- ✅ `从一次删库事故说起:我们把数据安全固化成了一份 SOP` —— 用「踩坑 / 实战复盘」模式带出 SOP,故事感更强

**原则**:SOP 是内容的**形式属性**,不是卖点;**解决什么问题、带来什么效果**才是卖点。标题要把卖点放主标题,SOP 放副标题或正文交代。

#### SEO 与长尾思维(标题的另一面:不只是钩子,还是搜索入口)

> 标题除了在信息流里抓眼球,还承担一个长期任务:**被搜索引擎收录,吃长尾流量**。本站是 Hugo + GitHub Pages,天生适合 SEO。下面的思维和上面的「钩子思维」不冲突——好标题两者兼顾。

**核心公式:标题 = 关键字 + 意图**。

- **关键字**:读者会搜的词。技术细节型文章(「XX 报错怎么解决」「XX 和 YY 怎么选」)吃的是 Google / 必应的长尾搜索流量——这类流量持续时间长(几年不断),不像掘金信息流只有几天热度。把读者真正会输入的搜索词写进标题。
- **意图**:读者搜这个词,是想**学**(教程)、想**理解**(原理)、还是想**解决**(报错)?标题要暗示意图,让搜索者一眼判断「这篇能回答我的问题」。

**长尾选题的来源**:

- **报错原文**:你踩过的坑,报错信息直接做标题或副标题(如 `Cannot read property of undefined:Vue 响应式异步更新的一个坑`)。下一个人遇到同样报错,搜出来就是你的文章。
- **"XX 怎么解决 / XX vs YY"**:这类搜索意图极明确,命中率极高。
- **工具名 + 具体场景**:`Claude Code 在大型 Monorepo 里的上下文管理`——比泛泛的「AI 编程」精准得多,搜索竞争小。

**和钩子思维的平衡**:

- 信息流平台(掘金)重钩子,搜索引擎重关键字。同一篇文章**掘金版偏钩子,博客版可偏关键字**(博客靠搜索,掘金靠点击)。
- 实操:主标题放钩子(数字/痛点/反差),副标题放关键字组合。这样两边都照顾到。

#### 自检三问(写完标题对照问自己)

1. **读者扫到这个标题,3 秒内知道文章讲什么吗?** 不知道 → 关键词没前置 / 主标题太抽象
2. **这个标题会让目标读者想点进去吗?** 不想 → 没有数字 / 痛点 / 反差 / 悬念中的任何一个
3. **内容能兑现标题的承诺吗?** 兑现不了 → 标题党,要么改标题要么补内容

三个问题任何一个答「不能」,标题返工。

#### 章节标题(文内标题,区别于文章标题)

- 只用 **一 / 二 / 三级**标题,不跳级。
- 三级标题下的并列内容,**用列表代替四级标题**。
- 章节标题说人话,不要用「关于 XX 的探讨」「深入剖析」这类空泛措辞。

### 强调与列表
- **关键词加粗**(中文标点)。
- 并列要点用**列表**,别堆在一段里。
- 步骤、规则、对比用列表或表格。

### 代码
- 代码块**精简**,只放关键几行,抽象掉无关部分。
- 不贴大段配置 / 日志。
- **代码例子优先用后端**(Java/Maven/Spring/SQL),少用前端例子。构建命令用 `mvn package`/`gradle build`,测试用 JUnit/Mockito 语境;除非文章本身就是讲前端(组件库、SSR 那些),否则不要放 Vue 组件、webpack 配置、`npm run dev` 这类前端例子。

### 句式
- 短句为主,长句拆开。
- 陈述 / 肯定语气,少感叹。

## 四、故事连贯(全站一个故事)

- **关于页**是故事主干(前端 → 全栈 → AI 开发)。
- **精选页**按三个阶段组织,是故事的地图。
- **每篇文章开头**用一两句点明:这件事发生在我的哪个阶段、代表什么能力 / 认知(自然带出,不强加)。
- 文章之间用 relref **互链**,形成网状叙事,不是孤岛。

### 成长阶段 → 文章归属(供组织与互链)
- **前端阶段**:组件库、微前端、Nuxt 性能、前端架构、前端团队基建、前端转架构师。
- **全栈阶段**:企业级前端架构(Vue+Node+Java)、低代码全栈、DDD、高并发 SSR+CDN、高并发低代码架构、技术驱动业务、Web 稳定性监控、多租户隔离、RBAC、Flyway、可观测性、压测。
- **AI 开发阶段**:序章(AI 编程之我见)、研发转型之我见、架构+AI 保障、工作流、多 Agent 评审、编译≠正确、契约闸、测试纪律、覆盖率、规范固化、事故即规范。

## 五、修订现有文章时的要点

- **语气**:清掉小白 / 摸索 / 卖关子,改成专家判断口吻。
- **排版**:把超长段落(>7 行)拆成 ≤4 行的小段;补小标题 / 列表 / 加粗。
- **工具排序**:提到 AI 工具处,统一以 Claude Code、Codex 为主,**不要再列 Cursor**。
- **故事钩子**:开头可补一句点明在成长线上的位置(自然、不强加)。
- **保留**:事实、数据、技术结论、作者原有观点**不动**。只改语气和排版,不重写内容。
- front matter 的 `title` / `weight` / `date` / `tags` 不动(除非明显错误)。
