# 保护片段（protected spans）— 去味不改事实

> 去 AI 味的第一原则：**先保信息，再谈风格**。任何改写都不能新增事实、删核心事实或改变责任主体。为「更口语」改坏原意 = 失败改写。

## 归类原则（一句话）

**承载事实 / 可复现 / 责任归属**的内容，一律不动字面量。遇到清单没列的类型，按这三条判断。

## 保护清单（代表项，非穷举）

### 技术字面量
- 代码块（` ``` ` 围栏）与内联代码（`` ` `` 反引号）
- URL / 链接 / 锚点
- API 路径、端点、HTTP 方法
- JSON / YAML / TOML 键名与值
- 配置项、参数名、环境变量名、flag
- 命令行（含参数）
- 报错日志、堆栈信息、状态码

### 版本与标识
- 版本号（`v0.124.1`、`3.2.0`）
- 文件名、路径（`content/posts/x.md`）
- commit hash、分支名、tag
- 工具名 / 库名 / 框架名（保留原名，不擅自中译）

### 事实与归属
- **数字与其修饰对象的配对**（「QPS 高两个数量级」不能拆成「快了很多」）
- 人名、团队名、公司名
- 引用原文（引号内、引用块内）
- **责任归属**（谁做的决定、谁的坑、谁背锅）
- **实体关系**（X 做 Y / X 基于 Y / X 处理 Y）
- 日期、时间点、版本时间线

## 分析-输出一致性检查（防幻觉）

改写后、输出前，过一遍这三条：

1. **关系回指**：输出里每个「X 做 Y / X 基于 Y / X 处理 Y」都要能回指原文的同一谓词。不能凭「同段共现」推断关系。
2. **无中生有禁止**：输出不能出现原文没有的工具、产品、平台、功能、能力、实现关系或指标。
3. **强度保真**：同义改写不能改变谓词的方向、完成态、强度或效果类型。「提升效率」不能扩成「节省时间 / 成本」，「已经改善」不能弱化成「涉及」。

### 典型翻车

- ❌ 原文「积累了数据」→ 改成「系统能处理 AI 生成文本」（编造能力）
- ❌ 同段提到「AI」和「中文表达工具」→ 改成「该工具处理 AI 生成文本」（共现当关系）
- ❌ 原文「效率提升 40%」→ 改成「会更快」（弱化强度 + 丢数字）

> 口诀：**删套话可以，造事实不行。原文没说的，输出不许说。**

## 保真优先于去味

当「去 AI 味」与「保事实 / 保语义 / 保责任主体」冲突时，保真赢。承载关键事实的抽象句，即使「有点像 AI」，也默认保留——宁可不删，不删错。
